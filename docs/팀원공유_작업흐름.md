## 4-1. 자주 나오는 용어 설명

- 분석 우주
  - 수집된 기사 전체가 아니라, 전처리와 필터링을 거친 뒤 **실제로 분석에 투입된 최종 기사 집합**을 뜻함
  - 이 프로젝트에서는 날씨 기사, 클로징 기사, 중복 기사, 토큰이 너무 적은 기사, 소프트뉴스를 제외한 뒤 남은 기사들 — 최신 수치는 [6-1](#6-1-01_필터감사--분석-우주를-확정하는-단계) 참고

- 전처리본
  - 원문 기사를 사람이 읽기 쉬운 형태로 정리한 중간 산출물
  - 기자명, 푸터, 방송 태그 등을 제거했지만 기사 본문 구조는 대체로 유지함

- 분석토큰
  - 실제 분석 모델에 넣기 위해 만든 최종 텍스트 입력
  - 형태소 분석과 불용어 제거를 거친 `tokens` 컬럼이 핵심임

- 토픽 비중(theta)
  - 한 기사가 특정 토픽을 얼마나 많이 담고 있는지를 나타내는 비율값
  - 이 프로젝트에서는 기사별 theta를 평균내어 "어떤 매체그룹이 어떤 의제를 더 크게 다뤘는가"를 비교함

- 기술 용어(짧게)
  - **LPOD / oid** — 네이버 뉴스 URL 매개변수. `LPOD`는 "언론사 목록 페이지" 모드, `oid`는 매체 식별 숫자(예 001=연합뉴스). 두 값 조합으로 특정 매체의 일자별 페이지를 호출
  - **BS4 (BeautifulSoup4)** — 정적 HTML을 파싱하는 파이썬 라이브러리. 네이버 뉴스는 초기 HTML 안에 본문이 들어있어 BS4만으로 충분(빠름)
  - **Selenium** — 실제 브라우저를 자동으로 띄워 페이지를 그대로 가져오는 도구. BS4가 못 받아온 기사를 사람이 확인할 때 사용(느림)
  - **LDA / K** — Latent Dirichlet Allocation. 문서들이 몇 개 의제(=K개)로 묶이는지 자동으로 찾아주는 모형. K는 의제 개수
  - **coherence / perplexity / seed** — LDA가 만든 의제가 일관적인지(coherence ↑ 좋음), 새 문서에 얼마나 잘 맞는지(perplexity ↓ 좋음)를 보는 점수. seed는 난수 시드 — 시드를 바꿔 여러 번 돌렸을 때 결과가 비슷하면 "안정적"이라고 봄
  - **wxc** — `word x category` 의 줄임. 같은 단어가 매체그룹별로 얼마나 다르게 쓰이는지(특화어 분포)를 보는 작업 이름
  - **log-odds** — 한 매체그룹에서 어떤 단어가 다른 그룹보다 얼마나 더 많이 쓰였는지 수치화하는 방식(Dirichlet 사전 결합). 단순 빈도가 아니라 "이 그룹의 특화어"를 뽑을 때 사용
  - **coverage** — 04 감성 단계에서 KNU 사전이 해당 기사 토큰을 얼마나 덮었는지(사전 적중률)
  - **polarity** — 한 기사의 정서값. KNU 사전에서 양성 단어 수 ─ 음성 단어 수 / 전체. 음수면 부정적

## 4-2. 크롤링·수집 파이프라인 (Colab 전용)

분석에 들어가기 전, 네이버 뉴스에서 매체별 **기사 URL과 본문**을 받아오는 단계임. 이 부분은 **Google Colab에서만 실행** — Drive를 마운트해 결과를 Drive에 저장함. 분석 단계는 로컬에서 돌려도 되지만 수집은 Colab 통일

### 단계 1 — URL 수집 (`언론사_네이버뉴스_url_수집_colab.ipynb`)
- 입력 — 매체 목록(`press_ranges`) + 수집 기간
- 동작 — 네이버 언론사 일자별 페이지(`news.naver.com/main/list.naver?mode=LPOD&oid=...&date=...`) 를 매일·매 페이지 순회하며 기사 URL만 추출
- 출력 — `링크_{press}_{기간}.json` (한 매체·한 기간 분의 기사 URL 목록 1개)
- 특징
  - 한 일자 안에서 페이지(1, 2, 3 …) 자동 감지
  - 임시 체크포인트로 중단·재개 지원 — Colab이 중간에 끊겨도 진행 상황 유지
  - 같은 기간 작업이 이미 완료됐으면(`링크_*.json` 존재) 자동 skip — 부분 실행해도 중복 안 함

### 단계 2 — 본문 수집 (`언론사_네이버뉴스_본문_수집_bs4_colab.ipynb`)
- 입력 — 단계 1이 만든 `링크_*.json`
- 동작 — 각 URL 페이지를 `requests` + `BeautifulSoup` 로 열어 **제목·본문·날짜·카테고리** 추출. 네이버 모바일 뉴스(`n.news.naver.com/mnews/...`) 초기 HTML에 본문이 들어 있어 정적 파싱으로 충분
- 출력 — `본문_bs4_{press}_{기간}.csv` (5컬럼: `link, pubdate, category, title, body`)
- 특징
  - 스포츠·연예 페이지로 리다이렉트되면 자동 분기해 별도 파서 사용
  - 오류 URL은 1회 재시도, 그래도 실패면 `본문_bs4_재실패_*.json` 으로 따로 기록 → 섹션 7-1(검수) 에서 사람이 확인
  - 폴라이트 스크래핑 — User-Agent 고정·기사 사이 랜덤 sleep 으로 서버 부담 줄임

### 단계 3 — 본문 통합 (위 노트북 마지막 셀)
- 동작 — 매체별 본문 CSV(`본문_bs4_{press}_*.csv`)들을 모두 읽어 하나로 합치고 `press` + `media_group` 컬럼 부착
- 출력 — `통합_본문_bs4_언론사_{기간}.csv` (이 파일이 전처리의 입력)
- 특징
  - 같은 `link` 가 두 번 있으면 자동 중복 제거(매체별 oid가 달라 충돌 거의 없지만 안전장치)
  - `_direct`(방송사 직접 사이트 트랙) 파일은 통합에서 제외

## 6. 분석 노트북별 역할

### 6-1. `01_필터감사` — 분석 우주를 확정하는 단계

#### 한 줄로
수집한 기사 전체에서 **분석에 실제로 쓸 기사들**만 골라내고, 골라낸 결과 = `분석 우주`로 못박는 단계임

#### "분석 우주" 라는 용어
- 통계에서 말하는 표본 공간(sample space)과 비슷한 개념을 빌려옴
- 이 프로젝트에서는 아래 다섯 거름을 거쳐 살아남은 기사들 = **분석 우주(universe)**
- 모든 후속 결과(의제 비중·감성 점수·매체그룹 비교)는 이 우주 위에서 계산됨 → 기준이 하나로 고정돼 있어야 결과를 서로 비교할 수 있음

#### 다섯 거름 (왜 각 거름이 필요한가)

| 단계 | 거르는 것 | 왜 거르는가 |
|---|---|---|
| 1 | **날씨·클로징 단신** | `[날씨]`·"뉴스를 마칩니다" 같은 정형 단신은 분석 가치가 낮음 |
| 2 | **같은 매체 안 중복**(within_press_dup) | 같은 매체가 같은 기사를 두 번 송고(예: 1보·2보) → 한 매체의 의제 비중이 부풀려짐 |
| 3 | **매체 간 중복**(cross_press_dup) | 연합뉴스 기사를 다른 매체가 그대로 전재 → 같은 의제가 여러 번 카운트되는 걸 막음 |
| 4 | **토큰이 너무 적은 기사**(`n_tokens<10`) | 사실상 본문이 비어있어 토픽 분석에 의미 없는 행, LDA가 흔들림 |
| 5 | **스포츠·연예 소프트뉴스** | 시사 의제 비교가 목적이라 별도 카테고리는 제외(토글로 포함 분석도 가능) |

- 핵심 의제 기사 `7,387건` 기준
